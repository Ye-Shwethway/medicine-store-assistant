# Configurable Operational View Engine

Status: **F6C architecture decision — locked for implementation planning**

## Purpose

MSA must not reproduce the current workbook by turning each worksheet into a canonical database table. The target system is a durable inventory domain with configurable spreadsheet-like operational views.

The guiding rule is:

> **Spreadsheet layout is configurable; inventory semantics are not arbitrary.**

This preserves the familiar Main Stock / Daily Usage workflows while allowing Web, Flutter, Telegram, ChatGPT and native AI agents to share one consistent backend.

## Product goal

The system should support:

- one Main Store and any number of Sub Stores;
- human staff and AI agents operating on the same inventory truth;
- survival without ChatGPT or Google Sheets;
- multiple clients over the same backend;
- user-defined or preset table layouts;
- spreadsheet-like editing with draft/confirm/save behavior;
- typed, audited domain operations instead of raw database mutation.

## Layer 1 — canonical inventory domain

Canonical data is normalized around stable business concepts, not worksheet coordinates.

Initial domain families:

- Store / Location
- Local Product
- Stock Lot
- CMS Catalogue Version / Catalogue Identity / Mapping
- Receipt Batch / Receipt Line
- Usage Event
- Adjustment / Correction
- Inventory Ledger / derived balance
- Reorder Configuration / Calculation
- Monthly Snapshot / approved archive outputs
- Fixed Assets as a separate domain
- Audit / Actor / Operation records

A worksheet row number, visible column letter, filter result, or tab name is never a canonical identifier.

## Layer 2 — field and computation registry

The backend exposes a typed registry of fields that may be projected into operational views.

A view column belongs to one of four semantic classes:

1. **ENTITY_FIELD** — direct metadata such as local item name, unit, expiry date, store, catalogue mapping.
2. **COMPUTED_FIELD** — deterministic projection such as current balance, this-month usage, expiry status, shortage date, calculated reorder quantity.
3. **COMMAND_EDITABLE_FIELD** — editable in a table, but Save translates the draft into one or more typed domain commands rather than raw row/column updates.
4. **DISPLAY_HELPER** — numbering, labels, filter helpers, presentation-only status, formatting or convenience metadata.

Each field definition may declare read source, write semantics, validation, formatting hints, location scope, aggregation behavior and required authority.

## Layer 3 — operational view definitions

A view definition describes how canonical fields are presented.

Possible properties:

- view name and preset type;
- store/location scope;
- row grain, normally product-lot or another explicit domain grain;
- ordered columns;
- column labels and widths;
- field/computation mapping;
- filters and sorting;
- grouping;
- conditional formatting rules;
- frozen/pinned columns;
- editable vs read-only columns;
- default export/print settings.

Users may start from a preset or build a custom table manually.

Changing a view definition must not mutate inventory history.

## Main Stock preset

The existing Main Stock layout is a compatibility preset, not the database schema.

Current source behavior indicates columns such as local item, expiry, unit, opening/base stock, received stock, current balance, reorder level, this-month usage, estimated request quantity, CMS mapping and price information.

The preset should preserve the familiar operational layout while mapping each column to the correct canonical field, computation or command.

Examples:

- `Items` -> local product/lot display identity
- `Expiry Date` -> lot expiry metadata
- `Remaining Stock` -> period opening/base stock projection
- `Received Stock` -> current-period receipt projection
- `This Month Usage` -> aggregate usage computation
- `Stock Status Today` -> derived current balance
- `Estimated Request Qty` -> reorder computation
- `CMS Price` -> current mapped catalogue price
- `Serial Code` / `CS Name` -> current catalogue mapping projection

Derived fields are never written merely because a user edits a rendered cell.

## Daily Usage preset

The existing Daily Usage sheet is a monthly pivot view over normalized usage events.

Canonical usage remains date-based:

`store/location + lot + usage_date + quantity + source + actor/operation`

The familiar Day 1–31 columns are generated by the view engine for the selected month.

Editing a day cell creates a draft usage operation for the corresponding date and lot. It does not update a `day_19` database column because no such canonical column should exist.

The existing compatibility behavior remains reproducible:

- Main Stock supplies structural/base lot context;
- day cells represent actual usage;
- monthly usage is the aggregate of day usage;
- current remaining is derived from opening/base + receipts - usage +/- adjustments;
- Main Stock and Daily Usage presets display the same underlying canonical state rather than maintaining independent truth.

## Derived / archive views

`This Month Received` and `Reorder Form` are primarily filtered/projection views.

`Final Reorder Form` is a working/approved output that may contain manual adjustment before submission. Only the approved/submitted result needs durable business-record preservation when required for monthly history.

These surfaces do not require separate canonical inventory tables merely because the legacy workbook contains separate tabs.

A future Master Data/archive output is generated from canonical monthly state and approved business snapshots.

## Spreadsheet-like edit model

Operational tables may feel like Excel/Google Sheets, but edits use a controlled draft transaction model:

`cell/table edits -> local draft -> semantic validation -> change preview -> Confirm & Save -> typed domain commands -> transaction -> read-back -> refreshed view`

A draft can contain multiple cell edits. Before commit the backend resolves their domain meaning and rejects ambiguous or incompatible combinations.

Examples:

- changing an item name -> product/lot metadata command;
- changing expiry -> lot metadata command with validation;
- changing reorder level -> configuration command;
- entering Daily Usage -> usage command;
- applying a CMS price update -> catalogue/mapping command;
- changing a current balance directly -> normally blocked or translated into an explicit adjustment workflow, never silent ledger overwrite.

## Shared human and AI operation layer

Human Web/Flutter edits and AI-agent MSA actions converge on the same typed backend command layer.

Human path:

`View Engine -> Draft -> Confirm -> Typed Command`

AI path:

`MSA Action -> Authority check -> Typed Command`

Both then use the same:

`validation -> authorization -> idempotency -> domain transaction -> audit -> read-back`

AI agents therefore do not receive raw SQL authority merely because they can operate inventory actions.

## Multi-store model

Store/location is a canonical dimension, not a separate table set per store.

The target supports one Main Store and unlimited Sub Stores through store-scoped stock state and transactions.

Presets or custom views may be scoped to a location, for example:

- Main Store — Main Stock
- Main Store — Daily Usage
- Sub Store A — Daily Usage
- Sub Store B — Current Stock
- All Stores — Expiry Review

Adding a store does not require cloning database schema.

Transfers between stores become typed inventory movement workflows rather than spreadsheet copy operations.

## Authority and concurrency

The view layer must respect actor/location permissions and multi-user concurrency.

A visible editable column does not by itself grant write authority. The backend remains authoritative for:

- actor permissions;
- allowed stores/locations;
- command semantics;
- optimistic/concurrency checks where needed;
- idempotency;
- audit;
- confirmation requirements for higher-risk operations.

## F6C consequence

Workbook parity analysis should now distinguish:

1. canonical domain fact or event;
2. derived computation;
3. command-backed editable presentation;
4. display/filter/archive-only behavior.

`This Month Received`, `Reorder Form` and most of the legacy archive formatting should not consume disproportionate schema-design effort.

F6C priority is Main Stock, Daily Usage, CMS catalogue/mapping, batch intake, lot identity, opening/receipt/usage/current-balance semantics, reorder calculation inputs, month rollover and store/location behavior.

## F6D implementation boundary

F6D may implement the normalized schema and fresh shadow import needed for the canonical domain, but it should not attempt to build the full configurable UI engine in the same slice.

Suggested order:

1. lock domain identities and store/location model;
2. implement canonical schema parity;
3. import a fresh shadow snapshot;
4. prove Main Stock and Daily Usage projections from DB;
5. then implement a minimal view-definition/field-registry substrate;
6. later add spreadsheet-like editing and custom view builder over proven typed commands.

No production canonical promotion is authorized by this document.
